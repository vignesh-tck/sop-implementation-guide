Implementation Engine
Solution Architecture

This document defines the solution architecture for the SoP Implementation Engine — a human-in-the-loop system that converts block-level urban-design recommendations into fundable, actionable next steps. Analysis is organized by domain — Funding, Zoning, and Policy — each following a common two-phase pattern: an interactive discovery process that builds a domain catalogue from external sources, and a recommendation-level analysis process that scores catalogued items against a block's individual recommendations. A deterministic scoring layer combines the resulting domain signals into a composite feasibility score for each block.

01 · Purpose, Scope & Principles

Purpose, Scope and Architecture Principles

Purpose. This document describes the solution architecture of the SoP Implementation Engine: a system that converts block-level urban-design recommendations into fundable, actionable next steps for municipal planners. Analysis is organized by domain — Funding, Zoning, and Policy — each following a common two-phase pattern of interactive catalogue discovery followed by recommendation-level fit scoring, with a deterministic layer aggregating domain signals into a per-block feasibility profile. This document defines that architecture and the decisions behind it.

Scope

In scope
  • Domain-based recommendation analysis across Funding, Zoning, and Policy, per the two-phase specialist pattern (Section 04)
  • Interactive, source-agnostic catalogue discovery per domain
  • Recommendation-level fit scoring per domain
  • Deterministic aggregation into a composite feasibility score and implementation profile
  • Human review and approval gating on every persistence path
Out of scope
  • Natural-language chat interface and vector-based retrieval
  • Multi-jurisdiction / multi-city deployment
  • Authentication, authorization, and multi-tenant access control
On delivery status: this document describes the architecture independent of how much of it is currently built. What is implemented, partially implemented, or not yet started as of a given date is tracked separately in Section 15.

Architecture Principles

These principles are binding on any change to the system. Where a proposed change conflicts with one, the principle governs unless explicitly revised here.

①
Human authorization precedes persistence
No write to the data store occurs without an explicit human confirmation. Every agent graph pauses at each decision point before committing state.
②
Deterministic computation for decision-bearing scores
The feasibility score and its sub-scores are computed by structured logic, never proposed by a language model. The model informs; it does not decide.
③
Provenance accompanies every derived fact
Source URL, verbatim excerpt, and extraction confidence are recorded alongside any value the system derives from an external source.
④
Control logic lives in configuration and prompts
Scoring thresholds and extraction instructions are externally editable constants, not embedded in conditional branching.
⑤
Idempotent persistence
Every write operation is safe to re-execute; re-running an agent updates existing state rather than duplicating it.

Assumptions and Dependencies

The architecture assumes continued availability of the Anthropic API for language-model calls, a managed Supabase PostgreSQL instance as the system of record, and a single-jurisdiction pilot (Bowie, Maryland, within Prince George's County) as the current deployment target. Delivery is scoped to a two-person engineering team. These assumptions are revisited in Section 12.

02 · Solution Overview

Two-Stage, Human-in-the-Loop Process Architecture

The system is built around two purpose-built LangGraph agents. Stage A is a live, interactive session that fills a funding catalogue from whatever sources a planner brings — it runs independently of any block. Stage B then matches that catalogue against one block's specific recommendations, with one LLM judgement per (recommendation, programme) pair. Nothing reaches the database in either stage without an explicit human confirmation.

SoP's own block data is loaded once, up front, by a script — it never goes through an agent. Funding data is the opposite: nothing is pre-loaded, and every programme in the catalogue was found, read and verified during a live session. Zoning and policy sources are named here as the intended targets for the scaffold agents, not as anything currently ingested.

04 · Domain Specialist Pattern

The Two-Phase Specialist Pattern

Analysis in this system is organized by domain — Funding, Zoning, and Policy each answer a different question about a block's recommendations, but all three are architected to follow the same two-phase pattern. Funding is the domain currently built end-to-end; Zoning and Policy are defined against the identical pattern and share its data-model shape, but their logic has not been implemented. This section describes the pattern generically; Sections 05–06 present Funding as its reference implementation.

Phase 1 — Discovery (block-agnostic)

An interactive session that builds a domain catalogue from external sources: a source is fetched, the agent asks what it cannot determine from the text, reports honestly what the source actually contains, extracts structured items with verbatim excerpts checked against the source, and confirms each item's geographic reach. A human confirms every stage before anything is persisted. The output is a domain catalogue table, independent of any specific block.

Phase 2 — Recommendation-Level Fit Analysis (block-scoped)

A block-scoped process that loads the domain catalogue and scores every catalogued item against each of that block's individual recommendations — one LLM judgement per (recommendation, item) pair, each carrying a score and a narrative. A human reviews the proposed fits, may adjust or reject any of them, and only approved fits are persisted as domain signals. Every specialist agent implements the same SpecialistAgent contract for this phase: run(), get_pending_review(), apply_feedback().

This section instantiates the Phase 2 pattern for the Funding domain. A planner selects a block. FundingAgent — an implementation of the SpecialistAgent contract — scores every catalogued programme against each of that block's individual recommendations, not the block as a whole. Scoring a programme against a whole block produced narratives too vague to act on ("supports community development"); scoring it against one recommendation gives the reviewer something concrete to agree or disagree with.

07 · Data Architecture — Implementation Profile

Gold Layer: The Implementation Profile

One row per block, computed by the Orchestrator once Phase 2 signals are approved. Two distinct layers combine to produce it, and they are easy to conflate: an LLM-proposed judgement at the individual-signal level, followed by deterministic arithmetic at the aggregation level. Neither layer does the other's job.

1
LLM proposes a fit_score — one signal at a time
For each (recommendation, programme) pair, the model outputs a fit_score (0–1) and a narrative. This is a judgement, not a fact, and it is the only point in the pipeline where a language model outputs a number that can end up in the data store.
2
A human reviews, adjusts, or rejects each proposal
Only fits a reviewer approves are persisted to funding_signals, at the score the reviewer settled on. An unreviewed model output never reaches this table.
3
Deterministic aggregation produces the domain sub-score
Fixed Python arithmetic counts how many approved signals fall into each fit tier and applies a fixed point value per tier (below). No model call happens at this step.
4
Deterministic weighted composite produces the feasibility score
The three domain sub-scores are combined by a fixed weighted sum. This is the number written to feasibility_score — again, no model call.
Feasibilityscore 0–100
=
0.40 ×funding score
+
0.35 ×zoning score*
+
0.25 ×policy score*

* zoning and policy are a hardcoded 50.0 today — ZoningAgent and PolicyAgent are scaffolds. See Limitations.

The gold layer is ~40% real, 60% placeholder by weight. Funding is a genuinely computed score over reviewer-approved signals. Zoning and policy contribute their configured weight against a constant. The dev console marks the placeholder sub-scores with an asterisk — the honest claim is "reasoned, reviewable funding matching," not "a fully-scored feasibility index."

Funding sub-score: tiered, not summed

Scored on reviewer-approved fits alone, deduped to the strongest fit per programme first (a block-level view can't let one versatile programme cap the score by counting its rows under four different recommendations).

09 · AI / LLM Integration Architecture

Large Language Model Integration Boundaries

The LLM produces two kinds of output: extracted facts (read from a source, with a verifiable excerpt) and proposed judgements (a fit_score and narrative scoring one recommendation against one catalogued item). Both are reviewable by a human before persistence — a fit_score is a genuine model output, not a deterministic value, but it never reaches a table unreviewed. What the LLM is never asked for, and never produces, is an aggregate: no model call computes a domain sub-score or the composite feasibility score. Those are fixed arithmetic over the set of human-approved judgements — see Section 07.

10 · Agent Orchestration Architecture

Agent Orchestration Architecture (LangGraph)

The framework choice hasn't changed — LangGraph's interrupt() and checkpointing are exactly what a human-approves-everything design needs. What changed is the topology: instead of fanning out to three parallel specialists, there are two independent graphs (Stage A and Stage B) and a thin coordinator, plus two scaffold agents that satisfy the same interface but don't run.

In use
LangGraph
  • interrupt() pauses a graph mid-run for exactly the review payload the console needs
  • Command(resume=...) continues from that exact point — no restart
  • Both agents compile independently; the Orchestrator only calls their public methods
  • Checkpointer is MemorySaver (in-memory) on both agents — see the risk callout below
Considered, not used
PydanticAI
  • Cleaner API for simple tool-calling agents
  • No native interrupt/resume — would have to be hand-rolled for a design where every stage pauses
Key operational risk: MemorySaver is in-memory, and uvicorn --reload fires on every file save — any edit while a session is paused destroys its state. Stage B has a fallback (resolve_block_id reads funding_signals.thread_id if the checkpointer is empty), so an approved analysis survives a restart. Stage A has no such fallback — an interrupted discovery session is simply lost. langgraph-checkpoint 4.2.0 is already installed for a Postgres-backed swap; see Limitations.

FastAPI Depends()

Upsert / Idempotency
every DB write
program_key is the catalogue's conflict target; (block_id, rec_id, program_name) is the signal's. Safe to re-run either agent.
Read Model (Gold)
gold layer
Only the Orchestrator writes block_implementation_profiles. Still true, though today only one specialist feeds it real data.
No Typed Schema Layer
known gap
backend/models/ (6 Pydantic files) was deleted Sep 29 — it had already silently drifted from schema.sql because nothing validated against it. Every layer now passes raw Supabase dicts. Restoring validation means wiring it into the API layer deliberately, not resurrecting the old files.

12 · Architecture Constraints, Limitations & Roadmap

Known Constraints and Forward Roadmap

The current implementation is scoped to a single jurisdiction. A config-driven, multi-city geography abstraction — pluggable source connectors, a spatial geo_lookup rebuilt per city — does not exist today. This section states plainly what is hardcoded, what portability provisions already exist, and what building a second city would actually require.

Identified Constraints

Bowie / PG County hardcoded
GEO_PROMPT in funding_discovery.py states "Prince George's County, Maryland (FIPS 24033)" directly. A second city needs a prompt edit, not a config change.
No spatial join layer
Geography matching is tract_geoid string equality plus an LLM-recommended geo_scope tag — no PostGIS ST_Intersects, despite PostGIS being provisioned on the Supabase instance.
In-memory checkpointer
MemorySaver on both agents. A server restart loses any paused session — Stage A has no recovery path at all.
Zoning / policy are placeholders
Constant 50.0, not a score. 60% of the feasibility weight rides on two agents that have never run.
Deterministic eligibility unwired
CDBG income rule and NMTC tract lookup (tools/cdbg.py, tools/tract_eligibility.py) are intact but disconnected — assess_fit reasons from programme text alone, with no hard eligibility check behind it.
No PDF ingestion
web_source.fetch() raises rather than reads a PDF — a real limitation for master plans and many grant NOFOs, which are routinely PDF-only.

Existing Portability Provisions

⚙
Config-driven weights
Feasibility weights and scoring thresholds live in config.py, not code — tunable per deployment without a redeploy of logic.
⬡
Source-agnostic discovery
Stage A already accepts any government URL — it was exercised against Maryland DNR pages, not built specifically for them. A different city's funding pages need no code change to be read.
↻
Geography-agnostic graph shape
Neither LangGraph graph encodes Maryland anywhere in its structure — only the discovery agent's GEO_PROMPT string does, which is a one-line edit, not a rearchitecture.

Roadmap: Path to Multi-City Support (Not Currently Planned)

→
Parameterize GEO_PROMPT's state/county/FIPS instead of stating Maryland literally — the smallest change with the largest unlock.
→
Re-wire tract_eligibility as a genuine cross-city geo_lookup once a second city's tract designations are loaded — the tri-state True/False/None shape is already correct for this.
→
Swap MemorySaver for the already-installed Postgres checkpointer before scaling session volume beyond one demo city.
→
Build ZoningAgent against a second city's real GIS source to prove the SpecialistAgent contract actually generalizes, rather than assuming it does from Funding alone.

14 · Quality Assurance & Evaluation Strategy

Quality Assurance and Evaluation Strategy

Accuracy here is closer to retrieval precision than a traditional ML metric: when the system says a funding programme fits a recommendation, is that judgment reasonable and traceable to a real source? Three complementary approaches — the third is already built into the schema, not bolted on for evaluation's sake.

01
Manual Spot-Check
Gold Standard Eval Set
Pick a handful of Bowie blocks. Manually research what funding actually applies to their top recommendations. Compare to what Stage B produces, per recommendation, not per block.
Simple · high credibility
02
LLM-as-Judge
Faithfulness Evaluation
A second model call could check whether each fit narrative is faithful to the programme's own eligibility notes. Not yet implemented — the excerpt-verification guard in Stage A is the closest thing running today, and it already caught one bad excerpt.
Scalable · planned
03
Self-Reporting
Confidence + Provenance
Already built in and running. Every catalogue row carries extraction_confidence and a checked source_excerpt; every signal carries source_url and flags whether a score was reviewer-adjusted or an automated fallback. Nothing is hidden as more certain than it is.
Already in schema · zero extra work
Multi-city scalability is not yet demonstrated or fully architected. Today's system is genuinely Bowie / Prince George's County-specific in several places (see Limitations). What can be argued honestly is that the funding-discovery flow is source-agnostic in practice — it was pointed at Maryland state pages without being built for Maryland specifically — and that the score weights are config-driven. A second city is a real next step, not a claim already earned.
