Implementation Engine
Solution Architecture

A medallion data pipeline that takes block-level urban design recommendations and enriches them with real-world implementation signals — funding opportunities, zoning constraints, and policy context — to produce a feasibility score and actionable next steps for each block.

Geography: Bowie, MD Focus: Parks / Public Garden (anchor) Pattern: Bronze → Silver → Gold Version: 0.1 · Sep 2026
01 · Architecture Overview

End-to-End Pipeline

Public data from three focus areas is ingested raw, cleaned and geo-tagged, then spatially joined to SoP recommendation blocks. The gold layer assembles the final implementation profile per block — used by both the scoring engine and the natural-language front end.

Design principle: Each layer is independently queryable and reusable. 06 · Gold Layer

Implementation Profiles

The gold table is the final enriched output — one row per block, assembling everything needed to answer the question: "Can this recommendation actually get done, and how?" It includes a computed feasibility score and an LLM-generated action summary.

Feasibility score 0–100
=
0.4 × funding score
+
0.35 × zoning score
+
0.25 × policy score
LLM boundary: The feasibility score (0–100) is computed deterministically from structured silver table data — never by an LLM. The LLM only generates the plain-English summary_narrative on top of that already-computed score. This keeps the gold layer auditable and the source of truth grounded in real data, not model inference.
Weights are configurable. The 0.4 / 0.35 / 0.25 split is a starting point — funding is weighted highest because it's the most binary constraint (either money exists or it doesn't). These weights can be tuned per recommendation type, city, or user preference.

08 · LLM Roles

Where LLMs Fit — and Where They Don't

From the sponsor kickoff: "SoP Models + Structured Data = Source of Truth. LLMs = Extraction, Interpretation, and Interaction Layer." This is a hard architectural constraint — LLMs are never the source of truth, only the layer that extracts, interprets, and surfaces it.

Back-end
Extract & Structure
  • →Find relevant information from public sources
  • →Parse unstructured documents (grant PDFs, policy docs)
  • →Extract rules, eligibility, opportunities, constraints, deadlines
  • →Convert into structured implementation signals the gold layer can use

Front-end
Interact & Query
  • →Query the contextualized recommendation system

  • →"Which recommendations have funding available?"
  • →"Why is this scenario now higher priority?"
  • →"What should we do next?"

The Source of Truth Principle

SoP Models  +  Structured Gold Layer Data  =  Source of Truth
LLMs  =  Extraction  +  Interpretation  +  Interaction   layer only

Scoring: Deterministic vs LLM

✓ Correct score is deterministic 
# Score computed from structured data
score = (
  score_funding(funding_signals) * 0.40 +
  score_zoning(zoning_signals)  * 0.35 +
  score_policy(policy_signals)  * 0.25
)

# LLM only writes the narrative on top
narrative = llm.generate(
  prompt="Summarise this profile",
  context={score, signals, actions}
)
✗ Wrong LLM as source of truth 
# Never do this
result = llm.generate(
  prompt="Given these signals, what is the
  feasibility score for this block?"
)

# score = result["score"]  ← hallucination risk
# LLM invented a number, not computed one

09 · Scalability Design

Built for Multiple Cities

The architecture is designed from the start to work across geographies. Bowie is the prototype — but adding Philadelphia, Baltimore, or any USDOT partner city should require configuration, not code rewrites.

⚙
Config-Driven Geography
State, county, and city are parameters, not hardcoded values. A geography config object drives which data sources to pull, which zoning schema to use, and which policy documents to ingest.
⬡
Pluggable Source Connectors
Each data source implements a standard interface: fetch() → bronze_row[]. Adding a new funding program means writing one connector, not touching the pipeline. Sources are registered in a config catalog.
⊞
Standardized Silver Schemas
funding_signals, zoning_signals, and policy_signals have fixed schemas regardless of source geography. A Maryland grant and a Pennsylvania grant map to the same fields — only the values differ.
⊕
Geo Lookup is Rebuilt per City
The geo_lookup table is the only geography-specific artifact. Rebuilding it for Philadelphia means running the same spatial joins against Philadelphia block geometries — the gold layer logic is unchanged.
◎
Configurable Score Weights
Feasibility score weights (funding / zoning / policy) are stored in config, not code. Different cities or recommendation types can use different weights without a pipeline change.
↻
Incremental Updates
Bronze tables carry ingested_at timestamps. Silver and gold transforms are incremental — only reprocess rows where the source changed. Grant deadlines and policy updates propagate automatically.
10 · Agentic Architecture

Multi-Agent Workflow Design

Each focus area is owned by a dedicated specialist agent with its own tools and scope. An Orchestrator agent coordinates them, aggregates signals, and manages the final gold-layer write. Every agent is a small, resumable LangGraph workflow with explicit human interrupt points — nothing writes to the database without user approval.

Recommended
LangGraph
  • Built-in interrupt_before/after nodes
  • Checkpointing via MemorySaver — resume after human feedback
  • Explicit state graph — debuggable, observable
  • Parallel subgraph execution (fan-out to 3 agents)
  • LangSmith tracing out of the box
  • More boilerplate than PydanticAI
Alternative
PydanticAI
  • Cleaner, more Pythonic API
  • Strong type safety throughout
  • Lower overhead for simple tool use
  • Human-in-the-loop interrupts not native
  • Checkpointing / resume not built in
  • Harder to fan-out to parallel agents
Verdict: Use LangGraph for the orchestrator and all agent graphs. The interrupt/checkpoint pattern is exactly what you need — a user approves signals mid-run, and the graph resumes from that exact point rather than restarting. PydanticAI shines for defining typed tool inputs/outputs within each agent node, so the two can coexist.

11 · Code Design

Design Principles & Patterns

LangGraph and the code design patterns are two separate layers — LangGraph controls how the workflow runs, the patterns control what lives inside each node. They don't compete; they stack. This layering is also what makes parallel development between two teammates clean.

The Two-Layer Mental Model

LangGraph Layer Workflow orchestration StateGraph · nodes · edges · checkpoints · interrupt/resume · parallel fan-out
each node calls ↓
Code Design Layer What lives inside each node Repository · ABC · Pydantic models · Dependency injection
reads and writes ↓
Data Layer Supabase (PostgreSQL + pgvector) Bronze · Silver · Gold tables · geo_lookup · vector embeddings
Key insight: A LangGraph node is just a Python function. The design patterns govern what that function looks like inside — clean, testable, independently developable. LangGraph never cares about your repositories or ABCs. Your agent code never cares about graph state transitions.

Patterns Applied

Repository Pattern
agents → DB
Every table gets a Repository class. Agents never write SQL directly. Swap the real DB for a mock in tests without touching agent logic.
Abstract Base Class
agent contract
All specialist agents implement one ABC: run(), get_pending_review(), apply_feedback(). Orchestrator dispatches to any agent without knowing which one.
Dependency Injection
tools → agents
Tools (web search, GIS, LLM) are injected into agents, not hardcoded. FastAPI's Depends() wires everything at request time. Easy to swap in mocks for testing.
Pydantic Models
layer contracts
Every table has a corresponding Pydantic model. These are the shared contracts between agents and the DB. If the schema changes, both sides know at import time — not at runtime.
Upsert / Idempotency
DB writes
All agent writes use INSERT ... ON CONFLICT DO UPDATE. Safe to re-run any agent — no duplicate rows, no partial state. Agents are stateless between runs.
Read Model (Gold)
gold layer
Specialist agents write only to their own silver table. The gold layer is assembled exclusively by the Orchestrator. Gold is read-only from any agent's perspective.

How a LangGraph Node Uses These Patterns

agents/funding.py LangGraph node + Repository + DI 
# ── LangGraph node function ───────────────────────────────────
async def search_funding_node(state: FundingAgentState) -> dict:
    # agent injected via FastAPI Depends() — no hardcoded tools
    signals = await state.agent.search(
        block_id = state.block_id,
        features = state.rec_features,
        geo      = state.geo_context,
    )
    return {"candidate_programs": signals}


# ── LangGraph wires nodes — knows nothing about repositories ──
graph = StateGraph(FundingAgentState)
graph.add_node("search",  search_funding_node)
graph.add_node("review",  review_node)         # interrupt here
graph.add_node("write",   write_signals_node)  # repo.upsert()
graph.add_edge("search",  "review")
graph.add_edge("review",  "write")
graph.compile(interrupt_before=["review"], checkpointer=MemorySaver())
agents/base.py ABC — shared contract for all specialist agents 
from abc import ABC, abstractmethod

class SpecialistAgent(ABC):

    @abstractmethod
    async def run(self, block_id: str, ctx: BlockContext) -> AgentResult: ...

    @abstractmethod
    async def get_pending_review(self, thread_id: str) -> ReviewPayload: ...

    @abstractmethod
    async def apply_feedback(self, thread_id: str, fb: UserFeedback) -> None: ...


# Orchestrator dispatches to any agent — never imports FundingAgent directly
class OrchestratorAgent:
    def __init__(self, specialists: list[SpecialistAgent]):
        self.specialists = specialists

    async def run_all(self, block_id: str, ctx: BlockContext):
        return await asyncio.gather(*[
            agent.run(block_id, ctx) for agent in self.specialists
        ])
repositories/funding.py Repository — agents never write SQL directly 
class FundingRepository(BaseRepository):

    async def upsert(self, signal: FundingSignal) -> None:
        # INSERT INTO funding_signals ... ON CONFLICT (funding_id) DO UPDATE
        await self.session.execute(insert(FundingSignalORM)
            .values(**signal.model_dump())
            .on_conflict_do_update(
                index_elements=["funding_id"],
                set_=signal.model_dump(exclude={"funding_id"})
            ))

    async def get_by_block(self, block_id: str) -> list[FundingSignal]:
        rows = await self.session.execute(
            select(FundingSignalORM).where(FundingSignalORM.block_id == block_id)
        )
        return [FundingSignal.model_validate(r) for r in rows.scalars()]

13 · Evaluation Strategy

Demonstrating Technical Accuracy

Accuracy here is not a traditional ML metric — it's closer to retrieval precision. The question is: when the system says a funding opportunity or zoning constraint applies to a block, is that true? Three complementary approaches address this, and the third is already baked into the architecture.

01
Manual Spot-Check
Gold Standard Eval Set
Pick 5 Bowie blocks. Manually research what funding, zoning, and policy actually applies to each. Compare to what the system produces. Report precision: "System correctly identified X of Y funding opportunities."
Simple · High credibility · Do in DISCOVER phase
02
LLM-as-Judge
Faithfulness Evaluation
A second LLM call evaluates whether each extracted signal is faithful to the source document. Ask: "Does this extracted eligibility claim appear in this grant document?" Returns a faithfulness score per signal. Scalable — runs automatically on all 43 blocks.
Scalable · Increasingly accepted in AI evals
03
Self-Reporting
Confidence + Provenance
Already built in. Every silver signal carries a confidence score (0–1) and an extracted_text field linking back to the source. The system is honest about what it doesn't know. Low-confidence signals are surfaced as such in the frontend — accuracy is communicated, not hidden.
Already in schema · Zero extra work
Scalability is argued architecturally, not demonstrated at scale. Agents run in parallel (LangGraph fan-out), deploy independently, and are config-driven per geography. Swapping Bowie for Philadelphia requires one config change, not a code rewrite. The architecture doc is the scalability evidence — no need to run all 8,000 Philadelphia blocks in a demo.
